# M2: engine and the restore drill

Closed on 2026-11-26. This file is the spec for the parts that met the acceptance criteria below: what Part A found, the design, its decisions and the instructions for each later part. The parts, the checks they closed (A1 to E3) and their evidence are under [Closed](#closed), at the end. What outlives the milestone is summed up in [decision 0010](../decisions/0010-engine-run-model-and-stages.md).

## Acceptance criteria

Moved here from [../plan.md](../plan.md) at the close.

Starts with a spike on the orchestration choice ([decision 0003](../decisions/0003-orchestration.md)). Then the engine runs the restore drill against a real D1 database.

Accepted when:
- The spike confirms the orchestration choice or switches to the fallback, and the decision record is updated. It must show a run paused at a gate surviving a redeploy, and confirm there is no upper limit on the wait that would rule out multi-day approvals.
- The engine is deployed with Alchemy, behind Cloudflare Access, as two stages: staging and production.
- A restore drill run completes end to end: export, create temporary database, restore, verify, tear down, record.
- Killing the Worker mid-run does not lose the run.
- A step re-run after a crash produces no duplicate side effects.
- A forced failure at each step leaves no temporary database behind.
- A block reaches the outside world only through services the engine provides, and the engine provides only those the block declares.
- When a run reaches a final state, its event log is archived to R2 ([decision 0004](../decisions/0004-persistence.md)).
- After the drill works on the seeded sample database, it runs against Aemeth's own D1 index and checks that archived event logs replay to their recorded final states.
- Every transition is in the event log, and every step emits a trace span.

### The orchestration spike

[Decision 0003](../decisions/0003-orchestration.md) is confirmed. The spike was one Worker with a workflow of three steps and a gate: a slow action (it writes "started" to a D1 ledger, sleeps, writes "finished"), `DurableDeferred.await` as the gate, then a second action. Every write to the ledger also recorded which build made it.

**Locally, under `wrangler dev` with state kept on disk** (the Wrangler path: the four Durable Object classes re-exported, `CloudflareCluster.layer`, `CloudflareDurableObjects.setInitializer`):

- A run paused at its gate. The server was killed and started as a new build. The run was still `Suspended`, was approved, and completed on the new build. The first action was not run again (ledger count 1); the workflow body was replayed (count 2).
- A run was killed four seconds into its first action. After the restart the action ran again and finished: "started" twice, "finished" once. A step re-run after a crash is real, so a block's side effects depend on its idempotency key.

**On Cloudflare, deployed with Wrangler:**

- A run paused at its gate on build one survived a deploy of build two and completed when approved.
- **A deploy does not kill a busy Durable Object at once.** By default an active object keeps its old code for up to 300 seconds. The run approved just after the deploy finished on build one, and a run that was mid-step during the deploy finished its step undisturbed.
- A run paused on build two, then two deploys later approved, finished on build four.
- **A forced kill mid-step:** a deploy with `--durable-objects-code-update-mode immediate` reset a run six seconds into its first action. With no request sent to the workflow object, it started again on the new build within about 75 seconds and finished the step: "started" twice (builds three and four), "finished" once. The engine arms a guard alarm 60 seconds ahead while an attempt is in flight, which is what brought it back.

**On Cloudflare, deployed with Alchemy** (an Effect-native `Cloudflare.Worker` with `AlchemyCloudflareCluster.make`, a `Cloudflare.D1.Database` and a `Cloudflare.R2.Bucket`, stage `spike`):

- `alchemy deploy` created the Worker, the four SQLite-backed Durable Object classes, the database and the bucket in about 12 seconds. The README of `@effect/platform-cloudflare` says this path's live smoke test "has not yet been verified"; it works at these versions.
- A run paused at its gate survived an `alchemy deploy` of new code, was approved, and its last step wrote the run's log to R2.
- `alchemy destroy` removed everything.

**The same workflow ran on `WorkflowEngine.layerMemory`** under Bun with no infrastructure: `Suspended` at the gate, `Complete` after `DurableDeferred.succeed`, the action run once.

**There is no upper limit on a wait.** Read from the engine's source (`internal/workflowRuntime.ts`): a run suspended on a deferred has no alarm at all. Alarms are armed only for a durable clock or for an attempt in flight. The run is a row in the object's SQLite until something completes the deferred, and Cloudflare documents no expiry for stored data. The longest wait actually observed was minutes, across four deploys.

### What the spike showed about the design

- **A workflow cannot reach its own Durable Object's SQLite.** The workflow object's storage is internal to the engine: execution state, activity results keyed `name/attempt`, deferred exits and the clock table. `DurableObjectSqlClient` exists only inside an entity. So [decision 0004](../decisions/0004-persistence.md)'s "run events live in the run's Durable Object" cannot mean the workflow's object.
- **A log entity per run works.** An `Entity` (`RunLog`) with an `Append` and a `List` RPC kept the events in its own SQLite, and accepted an append only at the next `seq`. The workflow appended through `RunLog.client` inside activities. Across a mid-step kill and two restarts the log had each event once, in order. The owner chose this (decision 2).
- **Only completed activities are remembered.** An activity interrupted partway runs again from its start under the same name and attempt number. Nothing in the engine marks the second execution as a retry.
- **The workflow body replays from the top on every wake.** Anything outside an activity runs again each time, so the body must be deterministic and do its work only inside activities.
- **Alchemy's binding clients need a `RuntimeContext`** (`Cloudflare.D1.QueryDatabase`, `Cloudflare.R2.ReadWriteBucket`). A Worker's handlers have one per event; a workflow's handler layer, built once at init by `AlchemyCloudflareCluster.make`, does not, and the init program may not require it. The spike read it at init with `Effect.serviceOption(RuntimeContext)` and provided it to each binding call made from an activity. That typechecked and ran. It is the one awkward seam between the two libraries.
- **In an Alchemy Worker there is no wrangler file, no class re-export and no initializer.** `AlchemyCloudflareCluster.make` registers the four classes, and Alchemy owns the bindings and the SQLite class migrations. Durable Object storage survived each deploy.

### D1

Run with Wrangler against the account, which uses the same REST endpoints a block will; the documentation was read for the rest.

- **Export, create, import and delete work end to end.** A database was exported (2.8 s), a new one created, the dump imported into it (2.1 s), the rows of both compared equal (14 rows, same SHA-256 over the rows in key order), and the new one deleted.
- **An export is taken at one bookmark, and the database is unavailable to queries while it runs.** The response's `at_bookmark` "will not change for the duration of the export task". The signed download URL lasts one hour. The export must be polled or it cancels. An export cannot be taken at a past bookmark.
- **An export returns no row count and no checksum,** and **D1 SQL has no hash function**: `md5`, `sha1`, `sha3` and `crc32` are each "no such function", and `sqlite_version()` is not authorised. `quote()`, `typeof()` and `PRAGMA table_list` work. So the figures the drill compares are computed in the Worker (decision 4). This closes the "not yet verified" item on export consistency in [../versions.md](../versions.md): the export is one consistent state, and its figures cannot be taken with it.
- **A database has a name and nothing else.** There are no tags or labels. A 75-character name and a name with capitals and underscores were both accepted, though the documentation suggests under 32 characters. So a temporary database's run tag is in its name (decision 5).
- **A database created at run time cannot be bound to the Worker.** It is reached through the REST `query` and `raw` endpoints: 30 seconds per request, 100 bound parameters, and the account-wide limit of 1,200 API requests per five minutes.
- **Import is init, upload, ingest, poll,** with an MD5 of the file as its etag. A Durable Object's outbound request body is capped at 100 MiB, which bounds the upload. Both export and import block the database while they run.
- **Create and delete need the `D1 Write` permission,** which is for the whole account. A token cannot be limited to one database, so "production is never written" rests on the validator's `NeverWritten` and on the blocks, not on the token.
- **Time Travel restores in place** to a bookmark or a time, through REST as well as Wrangler, for 30 days on Workers Paid. It cannot clone. Recipe 4's revert step (M7) can use it; the item stays under "Not yet verified" until M7 runs it.

### Durable Objects, R2, Access and tracing

- **Point-in-time recovery exists for SQLite-backed Durable Objects,** for the past 30 days, and only from inside the object (`getCurrentBookmark`, `getBookmarkForTime`, `onNextSessionRestoreBookmark`). Nothing backs up or exports an object's storage from outside. This closes the item in [../versions.md](../versions.md). M2 builds nothing on it: a run in flight still exists only in its objects, as [decision 0004](../decisions/0004-persistence.md) says.
- **Limits that matter:** 10 GB of SQLite per object, 8 MB per row, 30 seconds of CPU per request by default, 10,000 subrequests and 1,000 D1 queries per invocation on Workers Paid. An alarm handler has 15 minutes of wall time and is retried up to six times.
- **How objects take new code is a Worker setting:** `deferred` with a delay up to 86,400 seconds (default 300), or `immediate`. Alchemy exposes it as `codeUpdateStrategy`.
- **An R2 object can be written once.** From the Worker binding, `put(key, value, { onlyIf: new Headers({ "If-None-Match": "*" }) })` wrote the object the first time and returned `null` the second, leaving the first value. Run on the account; the documentation states this only for the S3 API. Bucket locks can also forbid overwriting and deleting under a prefix.
- **Access was not shown working.** The Alchemy Worker's `access: { policies }` prop failed twice for account reasons: first "Access is not enabled" (the owner then turned Zero Trust on), then `auth.forbidden`, because the Alchemy login was made with Basic permissions, which do not include Access. Read from the documentation and Alchemy's source: the prop creates an Access application that covers the Worker's workers.dev hostname, routes and previews, so no custom domain is needed; the Worker reads the identity from `Cloudflare.Access.Context` (`ctx.access`) and does not parse the token itself; a service token carries no email, and its client ID is in `common_name`. Worker-level Access rejects WebSocket connections, which the design session before M3 must know.
- **Tracing was not run.** Read from the documentation: `CloudflareTracer` in `@effect/platform-cloudflare` records Effect spans into the trace Cloudflare already collects for each invocation, and Alchemy wraps it as `Cloudflare.Telemetry()`. Cloudflare can export those traces to an OTLP destination. Workers tracing is in open beta, and stored traces are billed from 2026-12-01. A span created in one invocation cannot be the parent of work in a later one, so a step's span must open and close inside the activity that runs it.

### Alchemy

Read from alchemy.run and the installed source, and run where the spike used it.

- **A stack is `Alchemy.Stack(name, { providers, state }, effect)`** in `alchemy.run.ts`. `Cloudflare.state()` keeps state in a Worker with a Durable Object on the account, one for every stack and stage, set up once with `alchemy state bootstrap`. `Alchemy.localState()` writes `.alchemy/` files; the spike used it.
- **A stage** comes from `--stage` or `$ALCHEMY_STAGE`, is read in the stack as `(yield* Stack).stage`, and is part of every physical name: the spike's Worker was `aemethspike-engine-spike-f2awngrgv6t2ak76`.
- **Credentials** are a profile (`alchemy profile edit --add Cloudflare`, kept in `~/.alchemy`), or under `CI=true` the variables `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`. Wrangler's login is not used. The Basic OAuth permissions were enough for Workers, Durable Objects, D1 and R2, and not for Access.
- **`alchemy destroy` deletes a D1 database with its data.** An R2 bucket with objects needs `forceDestroy: true`. `RemovalPolicy.retain` keeps a resource.
- **Alchemy ships a test harness,** `@alchemy.run/test`, that deploys a stack to a stage, runs a suite against it and destroys it, and a documented GitHub Actions workflow for a stage per pull request. Neither was run.
- **Alchemy runs under Bun.** The Worker is bundled with rolldown at deploy time. The spike's bundle was built from `import.meta.url` in a single package; a Worker that imports workspace packages by `workspace:*` was not tried.

## Design

### Shape

```
packages/core     adds: run inputs on RunStarted, the written form of values, valueFits,
                  decide(recipe, state, sizeOf), followsRecipe(recipe, log)
packages/blocks   adds: the contract an implementation follows, and an implementation beside
                  each declaration the restore drill uses
apps/engine       the Worker: the run workflow, the RunLog entity, the services blocks get,
                  the API, the archive, the index
infra             the Alchemy stack: Worker, Durable Object classes, D1 index, R2 archive,
                  Access, the seeded sample database
```

`packages/core` stays pure. `apps/engine` is the only package that imports `effect/workflow`, `effect/cluster` or `@effect/platform-cloudflare`.

### A run is a workflow and a log

- **The log entity is the source of truth.** `RunLog`, one per run, keyed by the run ID, holds the events in its Durable Object's SQLite. `Append` takes an event without `seq` or `at`, plus a dedupe key. The entity reads its state, gives the event the next `seq` and the time from `Clock`, runs `transition`, and stores the event only if `transition` accepts it. A rejected event is returned as the typed `EventRejected` and stored nowhere. An append with a dedupe key it has already stored returns the stored event, so an activity that runs twice appends once. Because an entity handles one request at a time, the workflow and the API can both append without racing for a `seq`.
- **The log entity also holds the run's recipe and its secrets,** in tables of their own. The validated recipe document is stored when the run starts, and the workflow reads it from there on every wake, never from the bundle, so a deploy that edits or removes a recipe file cannot change a run already started. A secret is a value a block must hand to a later block and that must not be read by anyone else, such as an export's download link. Neither is an event: the recipe is named in every event by id and version, and a secret is never in an event, the archive or the API. Secrets are deleted when the run reaches a final state.
- **The workflow drives the run and holds nothing of its own.** Its body is a loop: read the state from the log, ask `decide` what comes next, do it, append what happened. Every read, every append and every block call is an activity, so a replay does none of them twice.
- **`decide(recipe, state, sizeOf)` is a pure function in core.** It returns the next thing to do: start a step (or the items of a for-each), open a gate, end the main phase with a given `main`, start an undo, start a `finally` step, or end the run with a given final event. `recipe` is the validated recipe, which holds each step's block, so the blocks are not passed again; `sizeOf` says how many items a for-each runs over, which is a value in the log and not in the state *(Part B)*. It is the half of the engine that knows the recipe; `transition` is the half that does not. It answers gap 28 of the [M1 spec](m1.md) from the other side: the engine cannot skip a step or an owed undo, because it only does what `decide` returns.
- **A rejected append is an answer, not a failure.** The API can append between the workflow's read and its own append: a cancel lands, and `transition` then rejects the workflow's `StepStarted` or `GateOpened`. On any `EventRejected` the workflow reads the state again and asks `decide` again. It does not run the block, and it does not fail. A second rejection of what `decide` then returns is an engine bug: the workflow fails with the rejection in its error, and the run is left for a person.
- **A step is three activities:** append `StepStarted`; run the block; append `StepSucceeded` or `StepFailed`. If the engine dies during the second, that activity runs again under the same attempt and idempotency key, and the log shows one attempt (decision 3).
- **A gate is a `DurableDeferred`.** The workflow appends `GateOpened` and awaits it. The API's approve and deny routes append `ApprovalGranted` or `ApprovalDenied` to the log first, with the identity from Access, then complete the deferred. The log entry is the fact; the deferred only wakes the workflow. **The wake is repeated until it lands.** Nothing else wakes a suspended run, so a route that appended and then died before completing the deferred would leave the run asleep with its gate closed. Each route therefore completes the deferred whenever the log shows that gate closed, whether its own append was stored just now, was a duplicate, or was rejected because the gate was already closed; completing a deferred twice is harmless. A repeated approve, deny or cancel from the caller is what recovers a lost wake, and `GET /runs/:id` does the same check, so reading a run also repairs it.
- **A cancel is an append.** The API appends `CancellationRequested`. If a gate is waiting and the cancel is in effect, it also completes the deferred, under the same rule as an approval, so the workflow wakes, reads the state and finds the cancel. Otherwise the workflow sees it the next time it reads the state, between steps (M1 decision 17). A cancel inside a failure handler changes nothing (M1 decision 18), so it does not wake a gate that waits there: a run woken to find its gate still open would have spent its wake *(Part B, decision 20)*.
- **Retries are new attempts.** A block fails with a typed error that says whether it may be retried. The engine starts the next attempt after a delay from a durable clock, up to a limit (decision 9). The failure of the last attempt allowed is logged with `retryable: false`, whatever the block said, so the log never shows a retryable failure that nothing retried.
- **The driver sits behind one small interface** in `apps/engine` ([decision 0003](../decisions/0003-orchestration.md)): start a run, complete a gate, read a run. The workflow module does not leak past it.

### Blocks

- **An implementation is code beside its declaration:** `implement({ spec, uses, run })`, where `run` takes the inputs and returns the outputs or a typed `BlockFailed { reason, message, retryable }`. `reason` is the typed error's name, which the log records as the error's `name`. A `Required` input arrives as its value and an `Optional` one as an `Option`. The contract is in `packages/blocks`, since the engine depends on that package and not the other way round *(Part B, decision 21)*.
- **A block gets a context and services.** The context has the run ID, the step, the attempt and the idempotency key. The services are Effect services the engine provides.
- **A block declares the services it uses, and gets only those.** An implementation lists them (`uses`), and its `run` is typed to require exactly that list, so using an undeclared service does not compile. The engine builds each step's layer from the list, so a declared-but-unused service is the only slack. The list is in code for M2 (decision 8).
- **The engine checks what a block returns.** `valueFits(type, value)` in core says whether a JSON value fits a `DataType`. Outputs that do not fit their declared types fail the step as `OutputTypeMismatch`, not retryable (gap 27).
- **Values have a written form** (gaps 7 and 26), used for run inputs and outputs: `Text` a string, `Integer` a whole number, `Boolean`, `Duration` and `Timestamp` whole milliseconds, `List` an array, `Struct` an object, and `Resource` `{ kind, id }`, where `id` is the provider's own identifier, such as a D1 database's UUID, or for a resource that is itself a secret, the name of a secret the engine holds for the run. `RunStarted` gains `inputs`, a record of these by input name, checked against the recipe's inputs with `valueFits` when the run starts. No events are stored anywhere yet, so `eventSchemaVersion` stays 1.

### The restore drill's blocks

The five D1 blocks act through the Cloudflare REST API with a token the engine holds, since a target is a recipe input and cannot be a binding. `record.restoreDrill` is the sixth implementation.

- **`d1.exportDatabase`:** compute the figures, export, compute the figures again. If they differ, production changed meanwhile and the step fails as retryable `SourceChangedDuringExport`. The figures are a row count and a SHA-256 over every user table in name order, every row in key order, each value through `quote()`, read in pages and hashed in the Worker. The signed URL, which lasts an hour and downloads the whole database, is stored as a run secret through an engine service; the `export` output is `{ kind: "cloudflare.d1.export", id }` naming that secret, so the link is never in the log, the archive or the API.
- **`d1.createTemporaryDatabase`:** create a database named `<namePrefix>-<runId>`. Re-run safely by looking for that name first.
- **`d1.importExport`:** read the signed URL from the run's secrets, fetch the dump and import it. A link that has expired fails the step as `ExportExpired`, not retryable. The import's etag makes a second import of the same file a no-op.
- **`d1.checkAgainstExport`:** compute the same figures on the temporary database and compare.
- **`d1.destroyDatabase`:** given a database, it reads the database's name and deletes it only if the name ends with this run's ID; if not, it fails as `RunTagMismatch` and deletes nothing. A database already gone is a success. **Given `None`, it looks for the run's database by name.** A create can succeed at Cloudflare and still be logged as failed, when the response is lost on every attempt; the step then has no output, and a cleanup that did nothing on `None` would leave the database behind. So the block gains an optional `namePrefix` input (version 2 of the declaration, and of the recipes that use it): with no database and a prefix, it looks up `<namePrefix>-<runId>` and deletes it if it exists. With neither, it is a no-op success, as before.
- **`record.restoreDrill`:** writes the drill's result to the run's row in the index (`result`), through an engine service.

### Persistence

- **The index** is a D1 database bound to the Worker, with one table in M2: `runs` (id, recipe id and version, state, started, ended, archive key, and `result`, a JSON value a record block writes, which for the drill holds the rows compared and the checksum). The engine updates it when a run starts and when it ends. Migrations are files that Alchemy applies on deploy.
- **The archive** is an R2 bucket. When the log reaches a final state the workflow writes `runs/<runId>.json`, the whole log as JSON, with the write-once condition, then records the key and the final state in the index. A second write of the same key is refused and treated as done.
- **Recipes** in M2 are the files in `packages/recipes`, bundled with the Worker and validated when it starts a run. A run keeps the document it started with in its log entity (see above). What stays open is a deploy that changes `decide` or a block under a run in flight: gap 9. Publishing and versions in the index come with the builder (M4).

### API

Behind Access, on the Worker's workers.dev hostname. Schemas come from core.

- `POST /runs`: start a run of a recipe with inputs. Returns the run ID, which the engine generates.
- `GET /runs/:id`: the run's state, folded from its log. It also repairs the run: a lost wake is given again, and a run recorded but never set going is set going *(Part B)*.
- `GET /runs/:id/events`: the log.
- `POST /runs/:id/gates/:step/approve` and `/deny`: recorded with the caller's identity.
- `POST /runs/:id/cancel`.

A request with no Access identity is refused. A person's identity is their email; a service token's is its client ID, written as `service:<client id>`.

### Deployment

- **One stack, three kinds of stage:** `staging`, `production`, and `pr-<number>` for a pull request. Every resource name carries its stage.
- **The Worker is an Effect-native Alchemy Worker** with `AlchemyCloudflareCluster.make`, as in the spike.
- **Production and staging keep the default deferred code update.** A `pr-*` stage uses `immediate`, so a test can kill a run mid-step by deploying.
- **Production data is retained on destroy** (`RemovalPolicy.retain` on the index and the archive when the stage is `production`). Other stages are destroyed with their data.
- **The out-of-band path is the same `alchemy deploy`** run by hand ([decision 0008](../decisions/0008-out-of-band-path.md)).

### Tracing

`Cloudflare.Telemetry()` on the Worker. Each execution of a step's block is one span, opened and closed inside the activity, named for the block, with the run ID, step, item, attempt and idempotency key as attributes. A step re-run after a crash therefore has two spans and one attempt in the log. The rail is a test with an in-memory tracer that fails if a step ran without a span.

## Decisions made in this spec

Change any of these by saying so; otherwise later parts follow them. Decisions 2, 3, 4 and 6 were put to the owner on 2026-11-24, and decision 16 after the review the same day.

1. **Decision 0003 is confirmed:** `effect/workflow` on `CloudflareWorkflowEngine`. The fallback was not needed and was not spiked.
2. **Accepted by the owner: a run is two Durable Objects,** the workflow and a log entity. The log entity holds the events, runs `transition` on every append and assigns `seq`. The wording of decisions [0003](../decisions/0003-orchestration.md) and [0004](../decisions/0004-persistence.md) is updated.
3. **Accepted by the owner: a step re-run after a crash logs nothing new.** The same attempt runs again with the same idempotency key. The log records attempts and outcomes; a restart is neither. Each execution has its own trace span.
4. **Accepted by the owner: the drill's figures are hashed in the Worker,** before and after the export, and a difference fails the step as retryable `SourceChangedDuringExport`.
5. **A temporary database's run tag is its name:** `<namePrefix>-<runId>`. D1 has no tags. The engine generates run IDs of 26 characters, lower case, sortable by time, so the name stays well inside what D1 accepted.
6. **Accepted by the owner: deployment state is in `Cloudflare.state()`,** shared by CI and the owner's machine.
7. **`decide` and `followsRecipe` are pure functions in core,** property-tested against the validator's paths and against `transition`, and mutation-tested with the rest of core.
8. **A block's services are declared in its implementation, in code,** not in `BlockSpec`. Putting them in the declaration would let the validator and the builder show them; that is recorded as a gap, not done in M2.
9. **Retries:** at most three attempts of a step, a `finally` step or an undo, with delays of 5 and 30 seconds on a durable clock. One exported constant. A recipe cannot change it yet (a gap).
10. **A for-each's items run side by side, at most four at a time.** The restore drill has no for-each; the engine supports it because `decide` and the tests cover every recipe shape.
11. **The M2 API is the six routes above,** with no recipe management.
12. **Blocks call Cloudflare through `@distilled.cloud/cloudflare`** if it runs in a Worker; if it does not, through a small typed client over `HttpClient` written for the endpoints the drill needs. Part D decides by running it.

### Found while building Part B

**What was built, where it differs from the instructions above:**

- **`decide(recipe, state, sizeOf)` and `followsRecipe(recipe, log)`.** Both take the `ValidRecipe` that `validate` returns, which now carries `resolved`: the recipe with every name looked up. Neither takes the blocks again. `decide` also takes `sizeOf`, because the number of items a for-each runs over is a value in the log, and the state does not hold values. Without it `decide` cannot tell a for-each that is over from one with items left.
- **`decide` returns one of nine things:** `RunSteps` (one piece of work, or a batch of a for-each's items), `OpenGate`, `EndMainPhase`, `RunUndo`, `EndRun`, and four that mean something else moves first or nothing does: `AwaitStart`, `AwaitGate`, `AwaitWork`, `Ended`. Each holds the resolved step, so the engine looks nothing up.
- **`followsRecipe` returns the path a finished run took,** as the validator would write it, or the first event that leaves the recipe with one of twelve reasons. An unfinished log follows its recipe so far. It reads the log and never calls `decide`.
- **Reading a step's inputs out of the log is in core** (`run/values.ts`): `valuesOf`, `sizeOf`, `inputsOf` and `undoInputsOf`. A for-each's output is the list of its items' outputs, there only once every item has succeeded.
- **`inputProblems(recipe, inputs)` is in core:** every input missing, unknown or of the wrong type.
- **`valueFits` is stricter than "a whole number" for two types:** a `Duration` is not negative, and a `Timestamp` is a time a `Date` can hold. A `List` holds at most 1,000,001 items *(after the review)*.
- **The log takes a fact without any of the envelope,** not only without `seq` and `at`: the log knows its run and its recipe too.
- **The workflow fails with `RunStuck`,** a typed error with seven reasons, when it cannot take a run further: the log is gone, the recipe no longer validates against the blocks deployed, or the log refused twice in a row what `decide` led to. The run's log is left as it is.
- **A run id is 26 characters, as a ULID is,** in lower case: ten of time and sixteen of randomness, from `Clock` and `Random`.
- **`apps/engine` has an `Engine` service** with `start`, `approve`, `deny`, `cancel` and `read`: the "one small interface" of decision 0003. The API of Part C is these calls behind routes. `approve` checks what was approved against the gate's declared outputs.

## Gaps found

1. **A block's services are not in its declaration** (decision 8), so the validator and the builder cannot show them.
2. **A recipe cannot set a step's retry limit or delays** (decision 9).
3. **The engine's token can write any D1 database on the account.** Cloudflare has no narrower permission. A separate account for targets would be the real boundary.
4. **The drill's figures cost one read of every row, twice on production.** Past a few hundred thousand rows that meets the API's rate limit. A database that large needs another check, such as sampled tables.
5. **A run in flight has no copy outside its two Durable Objects.** Their point-in-time recovery works only from inside the object, and the engine does not use it.
6. **The log does not show that a step ran twice after a crash** (decision 3). Tracing does.
7. **Worker-level Access rejects WebSockets.** Live updates in M3 need polling, server-sent events, or a hostname-based Access application.
8. **A drill makes production unavailable to queries for the length of its export.** "Production is only read" holds, but it is not untouched. For Aemeth's index that is a few seconds; a recipe has no way to say when a drill may run.
9. **A deploy can change the engine under a run in flight.** The recipe is kept with the run, but `decide`, a block's code and the names of the workflow's activities are whatever the latest deploy holds, and the workflow replays against them. A change to any of these must stay compatible with runs already started, and nothing checks that yet. A version of the engine recorded with the run, and refused on mismatch, would at least stop such a run instead of misleading it.
10. **Each turn of a run's workflow keeps a copy of the log.** The read is an activity, so its result, every event so far, is stored with the workflow. A run of n turns stores about n²/2 events there. For the drill that is a few hundred; a long for-each would want the read to return only what changed.
11. **A for-each's batch waits for its slowest item** (decision 22). Three items that end at once wait for the fourth before the next four start. The owner asked for the sliding window to be revisited; it is under "Later" in the plan.
12. **The log cannot say that a for-each over an empty list was reached.** `followsRecipe` writes it as passed whenever a later step ran, and a cancel just before it is written as a cancel before the step after it. This is M1's gap 29 seen from the engine.
13. **A second cancel by the same person leaves no event** (decision 25). The API has no request id to tell a repeat from a new request.
14. **`valueFits` does not check that a `Resource`'s id exists.** It is a non-empty string; whether it names a real database is for the block to find out.
15. **A retry's delay holds back the new items of its batch.** A batch of a for-each can hold a retry beside items that have not run yet, and the batch starts only once the retry's 5 or 30 seconds have passed. It goes with gap 11, and with the sliding window under "Later" in the plan.
16. **Cloudflare does not hold a span for every execution of a block, and cannot as the engine runs** (decision 34). Seen in two runs of two steps each on 2026-11-25: the span of the step after the gate was stored both times with all its attributes; the span of a run's first step was stored neither time; the span of a step that ran for 90 seconds was stored as 59,999 ms with no attributes; and an execution that was killed left nothing, as expected. **Why, read from the source of `@effect/platform-cloudflare` 4.1.5 (`internal/workflowRuntime.ts`):** a workflow's attempt never runs in an invocation of its own. `run(..., { discard: true })`, which `POST /runs` uses, `resume`, which an approval's wake uses, and the alarm after a kill each start the attempt and hand its promise to `waitUntil`, then return; the attempt goes on in the object after the invocation that started it has ended. `CloudflareTracer` records a span in the trace of the invocation whose async context it was made in, and says that a span made after that trace was sent is lost. So whether a block's span is stored depends on whether the invocation that set its attempt going was still open when the span ended. The engine opens and ends every span, which the in-memory rail checks. A fix would be upstream: the runtime running an attempt inside an invocation that waits for it. A draft of the issue is with the owner to file if wanted.
17. **A finished run whose archive could not be written is not archived later.** After six tries over about an hour the workflow is over (decision 28). A read of the run could repair it, as it repairs a lost wake.
18. **Access is not always in front of the Worker:** for some seconds after a stage is created, and at least once just after a redeploy. The engine refuses a request with no identity by itself. Whatever else Aemeth serves, the UI in M3 first, needs the same check and cannot lean on Access alone.
19. **A secret travels to the log entity as an RPC,** and the cluster keeps an entity's messages in that object's own storage. Whether a message is deleted once handled was not looked at. It is the run's own object either way, never an event, the archive or the API.
20. **`Events` returns a run's whole log in one message,** which the cluster limits to 2 MB. It goes with gap 10.
21. **The fixtures are in production's bundle,** switched off by a variable (decision 26). Leaving them out of the bundle would need a second entry module.
22. **Two drills of the same database at once fail each other.** D1 exports a database once at a time: a second export is refused while one runs, and queries of the database fail meanwhile with `7500 internal error` (seen in M2 Part D on 2026-11-26). `d1.exportDatabase` treats both as Cloudflare being away, and its three tries, 5 and 30 seconds apart, can end inside another run's export of a large database. Before production drills on a schedule, drills of one database are to be one at a time, or the export's retries to wait out an export in progress. Part E ran its drills one after another and set up no schedule.
23. **The archive check samples only the 50 runs that ended last** (decision 42). An archive object of an older run that has gone bad is not found until a check samples it, which none will. A sample spread over the whole index, or a check that walks it all in turns, would find it.
24. **The engine's token is named for D1 and can read every R2 bucket on the account** (decision 45), the owner's other projects' among them. Whether a token can be held to Aemeth's archive buckets was not looked at. It goes with gap 3.
25. **An archived log is read against today's `RunEvent` Schema** (`packages/core/src/run/archive.ts`), strictly. Every event carries `eventSchemaVersion`, and it is 1 everywhere so far. The first change to an event must give the archive a decoder per version, or every drill of Aemeth's own index fails `ArchiveDisagrees` on sound runs until 50 newer ones exist. The engine's own replay of an archive has the same need.
