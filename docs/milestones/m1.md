# M1: core

Closed on 2026-11-23. This file is the spec for the parts that met the acceptance criteria below: the research, the design, its decisions and the instructions for each group. The parts, the checks they closed (A1 to D3) and their evidence are under [Closed](#closed), at the end. What outlives the milestone is summed up in [decision 0009](../decisions/0009-recipe-format-block-contract-and-run-model.md).

## Acceptance criteria

Moved here from [../plan.md](../plan.md) at the close.

Block and recipe schemas, the validator, the run transition function and the first invariants. Pure code, no infrastructure.

Accepted when:
- A recipe is a graph of nodes and edges with typed inputs and outputs ([decision 0002](../decisions/0002-recipe-is-a-graph.md)).
- All six recipes in [recipes.md](../recipes.md) exist as recipe documents and are used as validator fixtures. Gaps in the format that recipes 2 to 6 expose are recorded, not necessarily closed.
- Recipes are files in the repository, a JSON Schema is generated from the recipe Schema, and CI runs the validator on every recipe file.
- The validator checks every path through a recipe and returns the failing path for each broken invariant.
- The validator rejects cycles and reports when a recipe exceeds the size and branching cap.
- The block contract requires a block to be safe to re-run after a crash, using a key derived from the run and step IDs.
- Blocks take their targets as typed recipe inputs and never name Aemeth's own resources.
- Every event records the recipe version and the event schema version.
- `transition(state, event)` covers every run state, and property tests check the run invariants over random event sequences.
- Mutation testing on `packages/core` meets the threshold set in M0.

## Part A findings

Every item was run in a scratch project on 2026-11-23 with `effect` 4.1.5, `@effect/vitest` 4.1.5, `vitest` 5.1.1, Bun 1.4.4 and Node 26.12.1. `ajv` 8.20.0 was installed in the scratch project only, as an outside JSON Schema validator. Versions are recorded in [../versions.md](../versions.md).

### Versions

Nothing M1 uses has moved since M0. `effect`, `@effect/vitest`, `vitest`, `@effect/tsgo`, `typescript`, `oxfmt`, `knip` and Stryker are still the latest releases. Oxlint 1.95.0 and tsrs `tsrs5` are out, but `@effect/tsgo` 0.73.4 still caps them at 1.94.0 and `tsrs4`, so both stay held back. M1 adds no runtime dependency to `packages/core`.

### JSON Schema from an Effect Schema

- **`Schema.toJsonSchemaDocument(schema, options)` is the API**, marked `@stability stable`. It returns `{ dialect: "draft-2020-12", schema, definitions }`, not a standalone document. To write a file, assemble `{ $schema: "https://json-schema.org/draft/2020-12/schema", ...schema, $defs: definitions }`.
- **`identifier` annotations become `$defs` entries** and `$ref`s. Unannotated schemas are inlined.
- **`onExcessProperty: "error"` emits `additionalProperties: false`.** Decode with the same option (`Schema.decodeUnknownExit(Recipe, { onExcessProperty: "error" })`) so the generated JSON Schema and the decoder agree on unknown fields.
- **`TaggedUnion` becomes `anyOf` over objects with a one-value `_tag` enum.** `Literals` becomes `enum`. `Int` becomes `integer` with bounds.
- **`isPattern` emits a `pattern` only if the RegExp has the `u` flag.** Without it the constraint is silently dropped: ajv accepted the node id `"Bad Id"` that the Effect decoder rejected. With `/…/u` they agreed. This is documented on `isPattern`. Oxlint 1.94.0 has `require-unicode-regexp`, which the preset does not turn on. Part B turns it on.
- **`Schema.Number` emits an `anyOf` that also allows the strings `"Infinity"`, `"-Infinity"` and `"NaN"`** (its JSON codec). Use `Schema.Finite` or `Schema.Int` in recipe documents; both emit a plain `number` or `integer`.
- **A recursive Schema works.** A `DataType` union with `List: { item: Schema.suspend(() => DataType) }` and an `identifier` became a self-referencing `$ref`. ajv accepted a nested list and rejected an unknown tag inside it.
- **ajv and the Effect decoder agreed** on four samples: a valid recipe, a bad node id, an unknown top-level field and an unknown binding tag. The Effect decoder stays the authority: the generated document is for editors and outside tools.

### Property tests

- **`it.prop` takes Arbitraries as well as Schemas.** Options go in the third argument: `{ arbitrary: { runs: 1000 } }` (`Arbitrary.CheckOptions`: `runs`, `size`, `maxDiscards`, `maxShrinks`, `seed`).
- **`Arbitrary.flatMap`, `map`, `array`, `all` and `Constant` build dependent generators.** A DAG on 1 to 12 nodes was generated by drawing a size, then index pairs, keeping only edges from a lower to a higher index. A false property ("no DAG has more than one path") failed and shrank to `{ nodes: 2, edges: [] }`.
- **`Arbitrary.filter` that rejects small values stalls.** Under `checkEffect` and `it.prop`, `filter(array, a => a.length > 0)` gave 0 runs and 1001 discards, with or without `size: 10` or `maxDiscards: 5000`, though sampling the same array gives non-empty values about half the time. Filtering an integer works. **Build generators constructively** instead: `minLength`, bounded `Int` ranges, adding the wanted feature (a back edge, a cycle) by construction.
- **Uniform random event sequences are too weak for `transition`.** Over 100 runs, sequences averaged 2.4 events, because a random `RunCancelled` or a rejected first event ends most of them. A planted bug (a finished step accepted a second `StepStarted`) was not found.
- **Guided sequences find it.** The generator draws a list of integers; at each step a helper lists the events that could arrive in the current state, including ones that must be rejected, and the integer picks one. The same planted bug failed and shrank to a 4-event trace. 1000 runs took 28 ms.
- **Coverage must be asserted, or a property can pass vacuously.** A counter showed the guided test never finished all three steps in 100 runs; with 1000 runs it did. Each property test over a generator keeps a counter of the states or shapes it reached, checked by a test that runs after it.

### Loading the recipe files in a test

- **`import.meta.glob("../recipes/*.recipe.json", { eager: true, import: "default" })` works in Vitest 5.** It found both files, and a file with `version: 0` failed decoding. The base tsconfig sets `types: []`, so the test needs the `import.meta.glob` types. `vite` is not a direct dependency, and Bun's isolated linker does not put it at the top of `node_modules`, so `vite/...` type references do not resolve. `vitest/importMeta` exists but declares only `url` and `vitest`, not `glob`: with that reference, `effect-tsgo tsc` fails with `Property 'glob' does not exist on type 'ImportMeta'` (run in the scratch project with `types: []`). **A local declaration works:** a `.d.ts` in the package declaring `interface ImportMeta { glob<T>(pattern: string, options: { readonly eager: true; readonly import: "default" }): Record<string, T> }` type-checked, and rejected a `glob` call in any other form.

### Graph algorithms

- **`effect/Graph` exists** with directed graphs, traversal and cycle helpers, but it is marked `@stability unstable` throughout. The validator needs only cycle detection, a topological order and path enumeration on a graph of at most a few dozen nodes, and these are hand-written (decision 10).

`Schema.TaggedUnion`, `TaggedStruct`, `Union`, `Literals`, `Record`, `Struct`, `optionalKey`, `brand`, `suspend`, `Class`, `TaggedClass`, `TaggedError`, `isPattern`, `isBetween`, `isMaxLength`, `decodeUnknownExit`, `decodeUnknownResult`, `toCodecJson`; `Result.succeed`, `Result.fail`, `Result.isFailure`; `Match.valueTags`, `Match.exhaustive`. The preset's `typescript/switch-exhaustiveness-check` is on, so a `switch` over `_tag` is checked for exhaustiveness.

## Design

This is the main design problem of M1 ([decision 0002](../decisions/0002-recipe-is-a-graph.md)): a recipe is data, blocks are code, and the validator must check on data what TypeScript cannot. Every name below is a proposal; the decisions that follow say which parts need the owner.

### Three documents, one direction

```
packages/core     Schemas and logic: DataType, BlockSpec, Recipe, RunEvent, RunState,
                  validate(), transition(), idempotencyKey(), invariants/
packages/blocks   BlockSpec values: what each block declares (no implementation in M1)
packages/recipes  The six recipe files, recipe.schema.json, and the test that validates them
```

`packages/core` still imports nothing from the repository. `validate` takes the block catalog as an argument, so core's tests use small catalogs of their own.

### Data types

`DataType` is a closed, recursive tagged union: `Text`, `Integer`, `Boolean`, `Duration`, `Timestamp`, `Resource { kind }`, `List { item }`, `Struct { fields }`. A `Resource` is a reference to something outside Aemeth, such as `{ kind: "cloudflare.d1.database" }`. Two types fit when they are structurally equal; there is no subtyping in M1. This is the check TypeScript cannot do across a recipe document.

### The block contract (`BlockSpec`)

A block's declaration, data only:

- `id`, `version` and a `title` for people, referenced from recipes as `{ block, version }`. *(`title` was added in Part B.)*
- `kind`: `Action`, `Check` or `Gate`. Outcomes follow from the kind: an action or check `Succeeded` or `Failed`; a gate is `Approved` or `Denied`.
- `inputs`: name to `Required { type }` or `Optional { type }`. An `Optional` input receives an `Option`: `Some` value or `None`. A block must handle `None`; a cleanup block such as "destroy the temporary database" treats `None` as a no-op success.
- `outputs`: name to `DataType`.
- `effects`: a list of `Reads { input }`, `Writes { input }`, `Creates { output, lifetime }`, `Destroys { input }`, where `lifetime` is `Temporary`, `Expiring` or `Durable`. Effects name the block's own inputs and outputs, never a concrete resource. A `Temporary` output must be destroyed by the run that created it (the always-on `TemporaryCleanedUp` rule). An `Expiring` one goes away by itself, such as a download link, so nothing has to destroy it. *(`Expiring` was added in Part C, decision 23.)*
- **Temporary resources carry their run's tag.** A block that creates a `Temporary` output tags the resource with the run ID. A block that destroys a resource under the run-created exemption (see `IrreversibleOnlyAfterApproval`) checks that tag first and, if it does not match the run, fails with a typed `RunTagMismatch` error instead of acting. That is an ordinary step failure: in an undo or `finally` step it is a failed cleanup and the run ends in `NeedsAttention`; in a main-path step the run ends `Failed` after undo. Either way the error is in the event log by name. The tags are written and checked by block implementations from M2; M1 puts the rule in the contract and the `Temporary` lifetime in the Schema.
- `undo`: `Undo { block, version, inputs }` (a compensating block), `NoUndo { reason }`, or `NothingToUndo` (only allowed when `effects` has no `Writes`, `Creates` or `Destroys`). A writing block with no undo has to say so, as `CLAUDE.md` requires. **An undo says how it is fed** *(Part C, decision 21)*: `inputs` maps each input of the undo block to `FromInput { name }` or `FromOutput { name }` of the block being undone, so the two blocks need not share input names. `blockSpecProblems(spec)` in core checks a declaration against itself: `NothingToUndo` only with no changing effect, every effect names a declared input or output, a gate has no `Writes`, `Creates` or `Destroys` *(added in Part B)*, and an undo is fed only from inputs and outputs the block declares *(Part C)*. The validator checks undo blocks like steps: the undo block must exist in the catalog at that version and must not be a gate; every required input of it is fed; each fed value has the input's type; a required undo input is not fed from an optional step input; and **an undo block changes only what its step changed** (decision 22): an undo input with a `Writes` effect must be fed `FromInput` an input the step's block `Writes`, or `FromOutput` an output it `Creates`; one with a `Destroys` effect must be fed `FromOutput` an output it `Creates`. Destroying what the step merely wrote is not taking the write back *(narrowed after the Part C review)*. A gate cannot declare an `Undo`: it ends `Approved` or `Denied`, never `Succeeded`, so its undo would never run.
- `rerun`: the literal `SafeWithIdempotencyKey`. There is no other value, so a block that is not safe to re-run cannot be declared. The engine passes each attempt `idempotencyKey(runId, stepId, phase, item)`, a pure function in core, where `phase` is `Forward` or `Undo`: the same run, step, phase and for-each item always give the same key, and a step's undo never shares a key with the step, so a provider that deduplicates on the key cannot mistake a rollback for the original call.

A block cannot name Aemeth's own resources because a `BlockSpec` has no field for a target: targets reach it only through its inputs, and the validator rejects a `Literal` binding for any `Resource`-typed input. Resources come from recipe inputs or from other steps' outputs.

### The recipe document (`Recipe`)

- `format: 1`, `id`, `version`, `title`, `description`.
- `start`: the id of the first main-path step. Every node that is not a `finally` step must be reachable from it.
- `inputs`: name to `{ type: DataType }`. Supplied when a run starts.
- `nodes`: each a `Step { id, block, version, inputs, forEach? }`. Each input is a `Binding`: `RecipeInput { name }`, `StepOutput { step, output }`, `OptionalStepOutput { step, output }`, `ForEachItem` or `Literal { value }`, where the value is text, a finite number, a boolean, or a list or record of those, and never `null`. A literal can supply `Text`, `Integer` (a whole number), `Boolean`, and a `List` or `Struct` of those; `Duration`, `Timestamp` and `Resource` have no written form and come from recipe inputs *(Part C, decision 24)*. `forEach { over: Binding, onItemFailure: "Stop" | "Continue" }` runs the step once per item of a `List`; in that step, `ForEachItem` is the current item, typed as the list's item type. `ForEachItem` anywhere else is an error. For-each steps do not nest. The list a for-each runs over is a `RecipeInput` or a `StepOutput`, not a literal or an optional output *(Part C)*, and a gate cannot be a for-each. A for-each step's outputs are lists: a block output of type `T` becomes `List { item: T }`, one entry per item in input order, and like any output it can be referenced only where the whole step is known to have succeeded.
- **Data travels on bindings, not on edges.** A step input names the output it takes (`StepOutput`); edges carry control only. This changes the wording of [decision 0002](../decisions/0002-recipe-is-a-graph.md), which has edges carry typed data as well; the owner approved the change (decision 6 below).
- **A `StepOutput` reference is valid only if the producing step has succeeded on every path to the step that uses it.** The validator reports any reference that is not guaranteed on some path, with that path.
- **`OptionalStepOutput` is for `finally` steps,** whose data may come from a step that did not run or did not succeed. It resolves to `Some` output or `None`, and may only bind an `Optional` block input. **A `finally` step may not use `StepOutput` at all:** on the path where the run is cancelled before its first step, no main-path step has succeeded, and an earlier `finally` step may have failed, so nothing is guaranteed. A `finally` step binds its inputs from `RecipeInput`, `Literal`, `OptionalStepOutput`, and `ForEachItem` if it is a for-each. Undo steps need no optional references, since a step's undo runs only after that step succeeded and is given its inputs and outputs. Recipe 1's "record the result" reads the checksum check's output this way, so the run is recorded even when the check failed.
- `edges`: `{ from, on, to }`, where `on` is an outcome and `to` is `Step { id }`, `End { result: "Succeeded" }` or `End { result: "Failed", undo }`, where `undo` is `Run` or `Skip`. Only a failed end carries `undo` *(made a union in Part B, after review)*. **At most one edge per node and outcome**, so control never forks: a run follows one path. An outcome with no edge ends the main path by default: `Succeeded` and `Approved` end it `Succeeded`, `Failed` and `Denied` end it `Failed`. A default failed end runs the undo phase. An explicit `End` overrides both: a failure handled by its own steps still ends the run `Failed`, and `undo: "Skip"` says the handler already put things right, so no undo phase runs (`finally` still does). In recipe 3, check `Failed` → `rollback` → `Succeeded` → `End { result: "Failed", undo: "Skip" }`; without `Skip`, the undo phase would undo the rollback itself and re-promote the new version. A successful end never undoes, so the Schema gives it no `undo` field: `undo: "Skip"` with `result: "Succeeded"` cannot be written. Several edges may enter one node, joining alternative paths.
- `finally`: an ordered list of steps that run after the main path ends, whatever its result (the "always runs" steps of recipe 1). **Every `finally` step runs on every path;** none is skipped. Data that may be missing reaches it through `OptionalStepOutput`.
- `invariants`: the rules from `packages/core/src/invariants/` this recipe asserts, with their arguments, such as `{ rule: "NeverWritten", input: "production" }`. The `rule` field is the discriminator.

The list editor in M4 shows a restricted shape of this graph (a chain with `Succeeded` edges plus `finally`), as decision 0002 expects.

### Paths

A path is what one run could do, in three phases:

1. **Main:** the main-path steps from `start`, with one outcome each, ending `Succeeded`, `Failed`, or `Cancelled`. A for-each step is one entry on a path, whatever the number of items, which is not known until the run: its outcome is `Succeeded` (every item succeeded), `Failed` (at least one failed; others may have succeeded), or `CancelledPartway` (see below). With `onItemFailure: "Stop"` the remaining items do not start; with `Continue` they all run.
2. **Undo:** if the main path ended `Failed` or `Cancelled`, and did not end at an `End` with `undo: "Skip"`, the undo of everything that succeeded and has one, in reverse order, each with its outcome. **Undo is per item:** for a for-each step, each item that succeeded is undone, in reverse item order, whether the step as a whole succeeded or failed. In recipe 5, if three consumers took the new credential and the fourth failed, the three are moved back. On a path this is one entry, "undo of the step's succeeded items", after a for-each that ended `Succeeded`, `Failed` or `CancelledPartway`, with outcome `Succeeded` or `Failed` (at least one item's undo failed). The per-item order and at-most-once rules are run invariants, checked on events in Part D, not on paths.
3. **Finally:** each `finally` step, in order, with its outcome.

**Cancellation is a path, not a shortcut.** A cancel takes effect only between steps, at these points: before a main-path step starts, including the first (the path has no entry for that step); while a gate waits (the gate's entry has outcome `CancelledWaiting`, *named in Part C*); and partway through a for-each, where items already running finish and no new item starts (`CancelledPartway`). A step already running finishes first (succeeds or fails), so no block is interrupted halfway and no undo has to cope with "maybe happened". Each such point gives a path that ends `Cancelled` and then runs undo and `finally` like a failure, so the restore drill's temporary database is destroyed after a cancel too, and the cleanup invariants are checked on those paths.

**A failure handler runs to its `End`.** Once a step ends `Failed` or `Denied` and the recipe has an edge for that outcome, the run is already failing, and the path has no cancellation points from there on: the handler steps run through to their `End`, and the run ends `Failed`, not `Cancelled`. A cancel requested then is recorded and changes nothing. So in recipe 3, check `Failed` → `rollback` → `End { result: "Failed", undo: "Skip" }` cannot be cut short between the failed check and the rollback, or between the rollback and its `End`; `AfterFailure` holds on every path and `Skip` is never bypassed. A cancel requested during the undo or finally phase also changes nothing: cleanup is never cancelled.

**Every cleanup is attempted.** A failed undo or `finally` step does not stop the ones after it: all of them run, and the run then ends in `NeedsAttention`, a final state that tells a person what was left behind. **On the validator's paths, cleanups fail one at a time** (decision 25): for each way the main phase can go there is one path on which every cleanup succeeds, and one per cleanup on which only that cleanup fails. That is n + 1 paths for n cleanups, where every combination would be 2^n. A run may still have several cleanups fail; no rule can tell that from one failing, which a property test checks. In recipe 1, a failed "destroy the temporary database" still lets "record the result" run. A cleanup invariant is met on a path where that cleanup succeeds, or where that same cleanup was attempted, failed, and the run ended in `NeedsAttention`. It is broken on a path where the cleanup is never attempted, even if some other cleanup failed and the run ended in `NeedsAttention`.

The run's final result is `Succeeded`, `Failed` or `Cancelled` from the main phase, replaced by `NeedsAttention` if any undo or `finally` step failed. The validator enumerates every path and runs every invariant on each. A violation carries the rule, its message and the path, so the checks panel in M4 can show it.

### Validation, in order

1. **Decode** with the Schema, rejecting unknown fields.
2. **Structure:** no two declarations in the catalog share an id and a version; unique node ids; `start`, edges, bindings, `finally` and the recipe's invariants refer to existing nodes, recipe inputs and outputs; `start` is not a `finally` step; every node that is not a `finally` step is reachable from `start`; a `finally` step has no edge in or out and appears once in `finally`; a `finally` step uses no `StepOutput`; at most one edge per node and outcome; edge outcomes fit the block kind; blocks, and their undo blocks, exist in the catalog at those versions; `ForEachItem` only in a for-each step. (`End` with `undo` only on a failed end is enforced by the Schema in stage 1.) *Added in Part C:* each block and undo block a step uses is consistent with itself (`blockSpecProblems`); a gate is not a `finally` step, a for-each or an undo block; the step `DestroysOnlyApproved` names as its gate is a gate. This stage hands on the recipe with every name looked up, so later stages never search for a step or a block.
3. **Size:** at most 64 nodes and at most 8 edges into a node.
4. **Cycles:** rejected, with the nodes on the cycle. Nothing below runs on a graph with a cycle, so no later stage can loop.
5. **Types and references:** every required block input is bound once; each binding's type equals the input's type; a literal fits the input's type; a for-each runs over a list; each undo block is fed, and changes only what its step changed, as the block contract says; a `StepOutput` names a step that succeeded on every path to the step that uses it, and otherwise the error carries a path where it did not; `OptionalStepOutput` appears only in a `finally` step and binds only an `Optional` input; no `Literal` for a `Resource`. **This stage does not enumerate paths.** "Succeeded on every path" is a dominance check, one pass over the DAG in topological order: the guaranteed set of `start` is empty, and any other step's guaranteed set is the intersection, over its incoming edges, of the source's guaranteed set plus the source if the edge is on `Succeeded` or `Approved`. When a reference fails, one counterexample path is built by walking back along an incoming edge that lacks the producer. The work is linear in the graph, so the path cap is not needed here.
6. **Paths:** enumerated as described under "Paths", all three phases and cancellation included. The walk counts as it goes and **stops at 10,000 paths**, reporting `TooManyPaths` with the cap. Because the cap bounds the walk itself, not an estimate of it, path checking always finishes (decision 0002), however many `finally` steps, undos or for-each steps multiply the count.
7. **Invariants:** every rule on every path.

Each stage returns all of its errors, as a tagged union, and the next stage runs only when the previous one passed. **Size is checked before structure** *(after the Part C review)*, although it is numbered 3: it needs nothing looked up, and running it first means no stage does work on a document larger than the caps. `validate` returns a `Result`; it does not throw.

### Invariants: the starting set

These are proposals for the owner to write or approve; the folder belongs to the owner. The first applies to every recipe; the rest are asserted by a recipe. Reading data from a step that did not succeed is not a rule here: stage 5 rejects it for every recipe.

| Rule | Holds when, on every path | Recipes |
|---|---|---|
| `IrreversibleOnlyAfterApproval` (always on) | A main-path or `finally` step with `NoUndo` that writes or destroys a resource, or creates a `Durable` one, runs only after a gate was `Approved`, **unless** the resource it writes or destroys is bound, through the recipe's wiring, to an output an earlier step in the same run created with `lifetime: Temporary`. Undo blocks are not covered (decision 22) | 2, 4, 5 |
| `TemporaryCleanedUp` (always on, Part C) | Whenever a step that creates a `Temporary` output succeeds, that output is cleaned up, in the sense of `CleanedUp` | 1, 4, 6 |
| `NeverWritten { input }` | No step writes or destroys a resource bound from that recipe input | 1 |
| `CleanedUp { step, output }` | If the step succeeded, a later step, undo or `finally` step that destroys that output succeeds, or that destroying step was attempted, failed, and the run ended in `NeedsAttention` | 1, 4, 6 |
| `RequiredForSuccess { step }` | A path whose main phase ends `Succeeded` passed the step with `Succeeded`, even if a cleanup then failed | 1, 4 |
| `NoWriteBeforeApproval { input }` | Nothing writes or destroys that input before a gate was `Approved` | 3 |
| `AfterFailure { step, then }` | If the step failed, the `then` step runs afterwards on the main path | 3 |
| `DestroysOnlyApproved { gate }` | Everything a step destroys is an output of the gate, or an item of one | 2 |
| `OnlyAfter { step, requires }` | The step runs only on paths where every required step succeeded, or was approved if it is a gate | 5 |

Each rule is one file in `packages/core/src/invariants/`, written against a view of a path in which every effect of every block that ran carries where its value came from (a recipe input, a step output and how it was created, an item of either, a literal, or nothing). The file's comment is the rule's exact wording; the table is a summary.

A `NoUndo` step that creates a `Durable` resource is covered because a failed run would otherwise leave something lasting with no approval and no cleanup: recipe 5's "create the new credential" either declares an undo (delete it) or comes after a gate. Creating a `Temporary` resource is not covered; `CleanedUp` handles it.

The exemption in the first rule is what lets the restore drill delete its temporary database with no gate, while a schema migration's irreversible step needs one. The validator checks the exemption statically, through the bindings; at run time the run-ID tag (see the block contract) stops an exempt destroy from acting on anything the run did not create.

**There is no per-recipe opt-out** from `IrreversibleOnlyAfterApproval`. Adding one needs its own decision record; any opt-out must be approved by a person when the recipe is published, and shown in the M4 checks panel.

### Run events and `transition`

- **Every event has an envelope:** `eventSchemaVersion: 1`, `runId`, `seq`, `at`, and `recipe: { id, version }`. `seq` starts at 0 and adds one per event. `at` is whole milliseconds since 1970 UTC *(Part D, decision 28)*, supplied by the engine through Effect's `Clock`; `transition` never reads a clock.
- **Every completion event names the attempt it ends** (`step`, `item`, `attempt`), since for-each items run side by side; `item` is absent for a step that is not a for-each. Gate events follow the same rule: `GateOpened` opens an attempt, and `ApprovalGranted` or `ApprovalDenied` ends it. A completion that matches no open attempt, or one that already ended, is rejected.
- **Events are facts:** `RunStarted`, `StepStarted { phase, step, item, attempt, idempotencyKey }`, `StepSucceeded { step, item, attempt, outputs }`, `StepFailed { step, item, attempt, error, retryable }`, `GateOpened { step, attempt }`, `ApprovalGranted { step, attempt, by, outputs }`, `ApprovalDenied { step, attempt, by }`, `CancellationRequested { by }`, `MainPhaseEnded { main }`, `UndoStarted { step, item, attempt, idempotencyKey }`, `UndoSucceeded { step, item, attempt }`, `UndoFailed { step, item, attempt, error, retryable }`, and the final events `RunSucceeded`, `RunFailed`, `RunCancelled`, `RunFlaggedForAttention`. An `error` is `{ name, message }`, where `name` is the typed error's name, such as `RunTagMismatch`. `outputs` is a record of JSON values by output name. *(Part D: `UndoFailed` gained `retryable`, decision 26; `MainPhaseEnded` holds one `main` value, decision 29.)*
- **Attempts are numbered from 1, and the next one follows only a failure marked `retryable`** *(Part D, decision 26)*. That holds for a step, a for-each item, a `finally` step and an undo alike. Every attempt of one piece of work carries the same idempotency key.
- **The log says which phase a fact belongs to,** because `transition` cannot look it up in the recipe. `StepStarted.phase` is `Main` or `Finally`. `MainPhaseEnded { main }` is the engine stating how the main path ended and whether the undo phase follows, taken from the recipe's `End`. `main` has the shape of a path's `main` in the validator: `{ result: "Succeeded" }`, `{ result: "Failed", undo: "Run" | "Skip" }` or `{ result: "Cancelled" }`, so a successful or cancelled end cannot carry an `undo` *(Part D, decision 29)*. `ApprovalGranted.outputs` holds what the gate approved (recipe 2's list of items), so a replay recovers it. The idempotency key's phase stays `Forward` or `Undo`: `finally` steps have their own step ids, so their keys cannot collide with a main-path step's.
- **Run states** are a tagged union: `NotStarted`, `Running`, `WaitingForApproval`, `Compensating`, `Finalizing`, and the final states `Succeeded`, `Failed`, `Cancelled`, `NeedsAttention`. `Running` and `WaitingForApproval` record their track: `Normal`; `CancelRequested` once a cancel is requested on the normal track; or `Handling` once a main-phase step starts after a different step failed or a gate was denied *(three values since Part D, decision 29)*. `Compensating` records the main result, `Failed` or `Cancelled`. `Finalizing` records the main result, `Succeeded`, `Failed` or `Cancelled`, since `finally` steps run after a success too. `NeedsAttention` records it as well.
- **Every started state holds the run's record:** its id, its recipe, the last `seq`, and one entry per piece of work (a step or for-each item, a gate, an undo) with its latest attempt and how that stands, in the order each first started *(Part D)*. Which cleanups have failed so far is read from it (`failedCleanups`), not stored twice. The timeline in M3 is this record.
- **Phase changes.** `MainPhaseEnded` is accepted when no main-phase attempt is open. With `result` `Failed` or `Cancelled` and `undo: "Run"` it moves to `Compensating`; with `Succeeded`, or `undo: "Skip"`, straight to `Finalizing`. The first `Finally` step start moves `Compensating` to `Finalizing`, once no undo attempt is open. A final event must agree with what was recorded: `RunFlaggedForAttention` if any cleanup failed, otherwise the one that matches the main result.
- **Cancellation goes through cleanup, between steps.** `CancellationRequested` is recorded in any state after `RunStarted` that is not final. On the `Normal` track, running or while a gate waits, no new main-phase attempt (step, for-each item or retry) may start after it; the attempts in flight end, and `MainPhaseEnded` follows. **One start is still allowed: the failure handler of a step that was in flight and then failed or was denied** *(Part D, decision 30)*. From there the run is failing, not cancelling, and the handler runs to its `End` (decision 18). A `result` of `Cancelled` is accepted only after a request made on the `Normal` track, and not when the step the run stopped at failed for good (unless it is a for-each cut short) or was denied: that run failed. A step whose last attempt failed and could have been retried may end the run `Cancelled`: a retry is a new attempt, and the cancel takes effect before it *(after the Part D review, decision 32)*. A gate still waiting is closed by the cancel. On the `Handling` track, and in `Compensating` and `Finalizing`, the request changes nothing. The run ends with `RunCancelled`, or `RunFlaggedForAttention` if a cleanup failed. A failed undo or `finally` step does not end the run early: the rest still run.
- **`transition(state, event)` returns `Result<RunState, EventRejected>`.** An event that does not fit the state is a typed rejection, never an exception. `EventRejected` carries one of 18 reasons, with the state's tag and the event's tag and `seq`. `replay(events)` folds a log from `NotStarted`.
- **`transition` is strict about order** *(Part D, decision 27)*. Control never forks (decision 1), so a step the run has not seen starts only when nothing is in flight; only the items of one for-each run side by side. A step does not run again once another has started, and is a for-each throughout or not at all. Undos run one at a time. A `StepStarted` or `UndoStarted` must carry exactly the key `idempotencyKey` gives for its run, step, phase and item.
- `transition` does not see the recipe, so it checks the order of facts, not which step comes next. Choosing the next step from a recipe and a state is the engine's job in M2. It follows that `transition` cannot know which steps have an undo, so it checks that every undo is legitimate, not that every undo owed has run. That completeness check needs the recipe and belongs to the engine's tests in M2.

Run invariants checked after every event in the property tests: `seq` increases by one; final states accept nothing; the recipe version never changes within a run; every completion event matches exactly one open attempt, so an attempt ends at most once; an attempt is numbered 1, or one more than a failed attempt that may be retried; no step starts while a gate waits; every approval or denial records who; no `Main` step starts after `MainPhaseEnded`, and no `Finally` step before it; after a cancellation requested on the `Normal` track or at a gate, no main-phase attempt starts except a failure handler; `MainPhaseEnded` has result `Cancelled` only after such a request; undos run only in `Compensating`, only for steps and for-each items that succeeded, each at most once, in reverse order; no undo runs after `MainPhaseEnded` with result `Succeeded` or `undo: "Skip"`; an undo's idempotency key differs from its step's, and a key belongs to one piece of work; a failed cleanup does not stop later cleanups; the final event is `RunFlaggedForAttention` exactly when a cleanup failed, and otherwise matches the main result.

3. **Accepted by the owner: a failed cleanup ends the run in `NeedsAttention`,** a final state for a person, not a hidden retry loop, after every remaining cleanup has been attempted. Cleanup invariants accept it. Cancellation also runs undo and `finally`.
4. **Accepted by the owner, refined: the starting invariants** in the table above. After the second review the owner also extended `IrreversibleOnlyAfterApproval` to `NoUndo` steps that create a `Durable` resource. The owner narrowed the exemption in `IrreversibleOnlyAfterApproval`: it covers only a resource created earlier in the same run by a block that declares that output `Temporary`, checked through the recipe's wiring, and at run time through the run-ID tag, which an exempt destroy verifies before acting, failing as `RunTagMismatch` otherwise. No per-recipe opt-out; adding one needs its own decision record, a person's approval at publish time, and display in the checks panel. The owner writes or approves each invariant in Part C.
5. **Accepted by the owner: three packages.** Schemas and logic in `packages/core`; block declarations in `packages/blocks`; recipe files, the generated JSON Schema and their test in a new `packages/recipes` (`@aemeth/recipes`, depending on core and blocks). The workspace, Vitest and knip globs already cover `packages/*`, but the root `tsconfig.json` lists each project by name, so B3 adds `packages/recipes` to its `references`; without that, `bun run typecheck` would not build it.
6. **Accepted by the owner: data travels on step input bindings, not on edges.** Edges carry control only. [Decision 0002](../decisions/0002-recipe-is-a-graph.md) says edges carry "control flow and typed data", so its wording is updated at M1's close. With it, the owner set the reference rule: a `StepOutput` is valid only if its step succeeded on every path to the step that uses it, the validator reports any reference not guaranteed on some path with that path, and `finally` steps may take optional references (`OptionalStepOutput`, resolved as `Option`; a cleanup block treats `None` as a no-op success). The owner's note suggested `optional: true`; it is a separate binding tag here, since the conventions prefer tagged unions over booleans. It replaces the earlier rule that skipped such a `finally` step, which would have skipped recipe 1's "record the result" whenever the checksum check failed. Why: one step may take inputs from several earlier steps that are not its direct predecessor (recipe 1's checksum check reads the production database, a recipe input, and the temporary database created two steps earlier), and a binding names its source exactly where an edge would have to be duplicated per input. Type checking is the same either way.
7. **CI validates recipes through `bun run test`,** not a separate script: `packages/recipes` has a test that decodes and validates every `*.recipe.json`, and a test that the committed `recipe.schema.json` equals a freshly generated one. A `generate` script in that package rewrites the file.
8. **Data types match by structural equality,** with no subtyping, in M1.
9. **`rerun` has one value, `SafeWithIdempotencyKey`,** so no block can be declared unsafe to re-run. `idempotencyKey(runId, stepId, phase, item)` is in core; the phase keeps a step's undo from sharing its key.
10. **The graph code is hand-written,** not `effect/Graph`, which is marked unstable. It is small and fully mutation-tested.
11. **Caps:** 64 nodes, 8 edges into a node, 10,000 paths. Numbers in one exported constant, so M4 can show them. The path cap bounds the enumeration itself.
12. **Repetition is unrolled.** Recipe 3's traffic stages are written out as a fixed series of steps. Recorded as a gap: a `stages` construct may come later.
13. **Property tests use constructive generators and assert coverage** (Part A findings). Event sequences for `transition` are guided by the current state.
14. **`require-unicode-regexp` is turned on** in `oxlint.config.ts`, so no pattern is dropped from the JSON Schema.
15. **Accepted by the owner: an explicit `End` chooses whether undo runs** (`undo: "Run" | "Skip"`), so a failure the recipe handled itself (recipe 3's rollback) is not undone a second time.
16. **Accepted by the owner: undo is per item.** Every succeeded item of a for-each is undone on a failed or cancelled run, even if the step as a whole failed.
17. **Accepted by the owner: a cancel takes effect between steps,** never mid-step. The validator has a cancellation path before each main-path step and at each gate; `transition` records the request and waits for the attempts in flight to end.
18. **Accepted by the owner: a failure handler runs to its `End`.** After a `Failed` or `Denied` outcome that the recipe has an edge for, there are no cancellation points; the run ends `Failed`. Cleanup is never cancelled either.
19. **Accepted by the owner: a cancel during a for-each stops new items.** Items already running finish, then the succeeded items are undone. The validator models it as one `CancelledPartway` outcome, without knowing the item count.
20. **Accepted by the owner: a recipe names its first step in `start`.** The validator checks that every non-`finally` node is reachable from it and that `finally` steps have no edges.

21. **Accepted by the owner (Part C): an undo says how it is fed.** `Undo { block, version, inputs }` maps each undo input to `FromInput` or `FromOutput` of the block being undone, in place of feeding by name. It answers gap 1.
22. **Accepted by the owner (Part C): undo blocks are exempt from `IrreversibleOnlyAfterApproval`, and bounded instead.** For every recipe the validator rejects an undo block that writes anything its step did not itself write or create, or destroys anything its step did not create (`UndoChangesUntouched`, stage 5). The destroy half was narrowed after the review: an undo that destroyed a database its step had only written to would otherwise have passed with no gate. Recipe 5's undo of "create the new credential" revokes it with no gate; a "delete repository" undo fed the source repository its step only read is rejected.
23. **Accepted by the owner (Part C): cleaning up `Temporary` outputs is always on.** `TemporaryCleanedUp` applies to every recipe, with no opt-out. A third lifetime, `Expiring`, is for what goes away by itself; it gets no exemption under `IrreversibleOnlyAfterApproval`. `CleanedUp` stays, for a recipe to assert on any other output. It answers gaps 2 and 4.
24. **Accepted by the owner (Part C): a literal supplies plain values only.** Text, whole numbers, booleans, and lists and structs of those. `Duration`, `Timestamp` and `Resource` have no literal form. It answers gap 7.
25. **Accepted by the owner (Part C, after the review): on the validator's paths, cleanups fail one at a time.** One path where every undo and `finally` step succeeds, and one per cleanup where only it fails. With every combination, a recipe of about 13 undoable steps could not be published. Every cleanup is still attempted on every path (decision 3).

26. **Accepted by the owner (Part D): an undo can be retried.** `UndoFailed` carries `retryable`, as `StepFailed` does. For a step, a `finally` step and an undo alike, the next attempt may follow only a failure marked `retryable`. A run ends in `NeedsAttention` only if the last attempt of some cleanup failed, so a cleanup that failed once and then succeeded does not flag the run.
27. **Accepted by the owner (Part D): `transition` is strict about order.** It rejects a log no recipe could produce: two steps in flight, a finished step run again, undos side by side or out of reverse order. An engine bug of that kind is a typed `EventRejected` the moment it happens. The cost: the undos of a for-each's items cannot run side by side without a later change.
28. **Accepted by the owner (Part D): an event's time is whole milliseconds since 1970 UTC,** what `Clock.currentTimeMillis` gives. The UI formats it.
29. **The log and the state cannot say what cannot happen.** `MainPhaseEnded` holds a `main` in the shape of the validator's (only a failed end has `undo`), and the track has three values (`Normal`, `CancelRequested`, `Handling`) in place of a track and a separate flag. This follows the convention in `CLAUDE.md` and the Part B change to `End`.
30. **A cancel does not stop a failure handler from starting.** If a cancel is requested while a step is in flight and that step then fails, or a gate is denied, the next step may still start, and the run is on the `Handling` track from there. The Part A wording ("no new main-phase attempt may start") would have kept the engine off a path the validator checked, and broken `AfterFailure` on it. This follows decision 18.
31. **`transition` checks the idempotency key.** A start whose key is not the one `idempotencyKey` gives is rejected, so "an undo's key differs from its step's" holds for every accepted log by construction, and no engine can pass a key of its own.
32. **Accepted by the owner (Part D, after the review): a cancel takes effect before a retry.** If the step the run stopped at failed and could have been retried, the main phase may end `Cancelled`. Before, the retry was rejected and so was `Cancelled`, and a person's cancel of a step that was failing for a moment was recorded as a failed run.

### Gaps found

What writing the six recipes showed the format cannot say, or says awkwardly. None is closed here; each names where it could be.

**The block contract**

1. **Undo inputs are fed by name, which couples a block to its undo.** `workers.shiftTraffic` and `secrets.deployCredential` each take a `previous` input they do not need, only so their undo block can be given it. It is also a hazard: a generic "delete repository" block with an input named `repository`, used as the undo of "fork repository" (whose own input `repository` is the source), would be fed the source. Recipe 6 avoids it with a block named for its input, `artifacts.deleteFork`. A mapping on `Undo { block, version, inputs }` would remove both problems. *For the owner, before C1 checks undo feeding.* **Answered in Part C (decisions 21 and 22):** the mapping exists, and an undo that changes what its step did not is rejected, which closes the hazard. The `previous` inputs remain: an undo still sees only its step's inputs and outputs, so a block must take, or return, whatever its undo needs.
2. **A `Temporary` output is cleaned up only if the recipe says so.** `d1.createTemporaryDatabase`, `artifacts.forkRepository` and `artifacts.issueToken` declare `NoUndo` and rely on a `finally` step, which a recipe must remember to assert with `CleanedUp`. An always-on rule, "every `Temporary` output a recipe does not hand on is destroyed on every path", would close it. *For the owner, in C3.* **Closed in Part C (decision 23)** by the always-on `TemporaryCleanedUp`.
3. **A lifetime is fixed per block.** The same "create a database" cannot be temporary in one recipe and durable in another; that takes two blocks.
4. **A resource that expires by itself has no lifetime of its own.** `d1.exportDatabase` declares its export `Temporary` with `NoUndo` and nothing ever destroys it. Under the rule proposed in 2 it would need an `Expires` lifetime. **Closed in Part C (decision 23):** the lifetime is `Expiring`, and the export declares it.
5. **A write to the run's own record has no effect to declare.** The `record.*` blocks write through an engine service, not to a resource the recipe names, so they declare no effects and `NothingToUndo`.
6. **There are no generic types.** A gate or a record block is typed by what it shows, so there is one per shape: five gates and three record blocks for six recipes.
7. **How a `Literal` is typed is not defined.** Text, integers and booleans are plain. A `Duration` or `Timestamp` literal has no written form yet; the recipes take every duration as a recipe input. *Part C's type stage must define it.* **Defined in Part C (decision 24):** they have none.

**Per recipe**

8. **Recipe 1: the extra check on Aemeth's own archive** (replaying archived event logs) is not written. It needs the engine and its archive (M2).
9. **Recipe 2: a list holds one kind.** Stacks and orphaned resources are two lists, two for-each steps and two destroy blocks, because there is no union type.
10. **Recipe 2: "no stack outside the preview stages is ever destroyed" has no rule.** It is a property of what the list block returns at run time, not of a path. It belongs in the block's implementation and its tests (M5).
11. **Recipe 2: a failed for-each exposes no per-item results.** Its outputs can be read only when the whole step succeeded, so the record step can say what was approved, not "what was destroyed and what failed". The event log has both.
12. **Recipe 2: "try both, fail if either failed" cannot be said.** With no `Failed` edge, a failed stack destroy ends the run before orphans are tried; with one, the run would then end `Succeeded` unless the node were duplicated.
13. **Recipe 3: the traffic stages are unrolled** (decision 12): three shift and check pairs, and three `AfterFailure` references.
14. **Recipes 2 to 6: a denied gate ends the run `Failed`.** There is no result for "a person said no", which is not a failure of the recipe.
15. **Every recipe: a failure handler is written per step.** Recipes 3, 4 and 5 each needed a `Failed` edge on every step whose failure must not fall through to the default undo; a missed one is silent. A recipe-level "on any failure after this point" would say it once. Until then, `AfterFailure` rules are the guard.
16. **Recipe 4: "revert where possible" is a restore to a bookmark** taken after approval, itself a write with `NoUndo`. A failed production migration goes to the same revert step as a failed smoke test. Whether D1's point-in-time restore fits is for M7.
17. **Recipe 5: "a partial failure leaves every consumer on a working credential" is not a path rule.** It holds through per-item undo (decision 16), a run invariant checked in Part D.
18. **Recipe 6: a long wait is an ordinary action.** `artifacts.awaitPush` takes its timeout as an input, and a cancel cannot take effect while it runs (decision 17 allows one only between steps and at gates), so a multi-day wait cannot be cancelled. A wait construct, or a third cancellation point, would close it.
19. **Recipe 6: a gate has no kind of approver.** "By a person or a policy" cannot be said.

**Found in Part C**

20. **A `finally` step cannot run a for-each over a step's output.** A `finally` step may not use `StepOutput`, and a for-each may not run over an `OptionalStepOutput`, since what "no list" means for a for-each is not defined. So a list of temporary resources made by a for-each can be destroyed only on the main path, where a cancel or a failure before the destroy breaks `TemporaryCleanedUp`. No recipe needs it yet. Letting an absent list mean "no items" would close it.
21. **A for-each that creates temporary resources and then fails leaks them.** Its list output cannot be read (gap 11), so no step can name what the items that succeeded created. `TemporaryCleanedUp` covers only a step that succeeded. A per-item undo that destroys what the item created does clean up, and is the way to write such a block today.
22. **An item of a list of temporary resources is not exempt under `IrreversibleOnlyAfterApproval`.** The exemption is for an output bound directly. A for-each that writes to each temporary copy needs a gate or an undo.
23. **The validator's errors, paths and violations are TypeScript types, not Schemas.** Nothing serialises them yet. The checks panel (M4) and the API will need Schemas for them, defined in core.
24. **Every violation is reported once per path.** A rule broken by one step is reported on every path through that step: 20 violations for one missing gate in recipe 4. The checks panel will want them grouped by rule and step, with one path shown.
25. **The validator does not model two cleanups failing in one run.** Its paths fail one cleanup at a time (decision 25). A future rule that depends on which combination of cleanups failed would need the fuller walk, which is kept in `paths.ts` and is exponential.

**Found in Part D**

26. **`RunStarted` does not record the run's inputs.** The values a run was started with are needed to replay it, but a `Resource`, `Duration` or `Timestamp` value has no written form yet (gap 7). The engine defines them in M2 and adds the field then.
27. **Outputs are JSON, not typed.** `StepSucceeded.outputs` and `ApprovalGranted.outputs` are records of JSON values by output name. Whether a value fits its block's declared output type is for the engine to check when the block returns it (M2).
28. **`transition` cannot tell that an undo is owed, that a step was skipped, or what order `finally` steps run in.** It does not see the recipe (see "Run events and `transition`"). A check of a log against its recipe, "this run followed one of the validator's paths", belongs to the engine's tests in M2.
29. **A for-each over an empty list leaves no event.** Its step never starts, so the log does not show that it ran. A `StepSkipped`-like fact, or an event for the for-each as a whole, would show it in the timeline (M3).
30. **A gate has one attempt and no time limit.** `GateOpened` is always attempt 1, and nothing in the log says a gate expired. If gates get timeouts (gap 18), that is a new outcome and a new event.
31. **The undos of a for-each's items run one at a time** (decision 27). For a long list that is slow. Letting the items of one step be undone side by side is a change to `transition` and to the "reverse order" invariant.
32. **`EventRejected` names its reason but not what it expected.** "Out of sequence" does not say which `seq` was due. The engine's logs may want that in M2.
33. **The log does not say whether a for-each ran to its end.** After a cancel request, `transition` accepts `Cancelled` for a run that stopped at a for-each with a failed item, whether the cancel cut the for-each short or it had already finished `Failed`, in which case the run was failing and should end `Failed` (decision 18). The number of items is not in the log. The engine's tests cover it in M2, with the recipe in hand; a fact for the for-each as a whole (gap 29) would let `transition` check it. *Recorded as a gap on the owner's answer to the Part D review.*

## Part C: the validator

### C1: structure, size, cycles, types

- Stages 2 to 5 of "Validation, in order", each returning all its errors as a tagged union.
- Property tests over generated DAGs (decision 13): an acyclic graph passes the cycle check; a graph with a constructed cycle fails it, names the cycle's nodes, and never reaches the path stage.

### C2: paths

- Stage 6: enumerate paths as described under "Paths", with all three phases and the cancellation points. Each path is a list of `{ phase, step, outcome }` entries plus its final result; a for-each step is one entry, and so is the undo of its succeeded items. The walk stops at the cap and reports `TooManyPaths`.
- Property tests: every path ends in a final result; undo entries are the completed undoable steps in reverse; every `finally` step appears on every path; after a failed cleanup every remaining cleanup still appears and the result is `NeedsAttention`; there is a `Cancelled` path before each main-path step on the normal track, at each gate and partway through each for-each, and each runs undo and `finally`; no path is `Cancelled` after it has followed a `Failed` or `Denied` edge; a for-each that ended `Failed` or `CancelledPartway` still has its undo entry; a path that ends at `undo: "Skip"` has no undo phase; a generated recipe whose paths exceed the cap stops at the cap, and one below it gives the same paths with a cap far above it.
